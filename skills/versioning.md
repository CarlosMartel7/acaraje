# Versioning

**Use this skill when** preparing a pull request from `develop` into `master`, or whenever
asked to bump, release or tag a version of Acaraje.

Acaraje follows [Semantic Versioning](https://semver.org) (`MAJOR.MINOR.PATCH`). The version
lives in `package.json` and is bumped **only** in a PR from `develop` into `master`, once per PR.
Every such PR is one release.

## Deciding the bump

1. List the commits in the PR: `git log --oneline master..develop`.
2. Take the highest bump that applies:
   - **MAJOR**: any commit marked breaking (`type(scope)!:` or a `BREAKING CHANGE:` footer),
     or any change that breaks existing users even if it isn't marked (see below).
   - **MINOR**: any `feat` commit.
   - **PATCH**: `fix` or `perf` commits, or `refactor`/`style` commits that change
     generated output or CLI behaviour.
   - **No bump**: only `docs`, `test`, `chore`, `ci`, or internal refactors.
3. When bumping MINOR, reset PATCH to 0. When bumping MAJOR, reset MINOR and PATCH to 0.

| Commits in the PR include… | Bump | Example |
|---|---|---|
| A breaking change | MAJOR | 1.4.2 → 2.0.0 |
| Any `feat` | MINOR | 1.4.2 → 1.5.0 |
| Only fixes or behaviour-changing refactors | PATCH | 1.4.2 → 1.4.3 |
| Only docs, tests, chores, CI, internal refactors | No release | stays 1.4.2 |

## What counts as breaking

Acaraje is a CLI that generates projects, so a change is breaking when it makes a user's
existing command, script or generated project stop working:

- Removing or renaming a CLI command or flag, or changing a flag's meaning (e.g. `--api`).
- Changing a default in a way that alters generated output (e.g. making `trpc` the default
  API layer instead of `rest`).
- Changing `acaraje.config.json` so projects generated by an earlier version can't be read.
- `acaraje update schema` producing code that doesn't fit projects generated by an earlier version.
- Raising the minimum supported Node version.

**Not breaking** (MINOR at most): new prompts with sensible defaults, new flags, new opt-in
options (like the tRPC API layer), and visual changes to the generated templates.

If you are unsure whether a change is breaking, ask the maintainer instead of guessing.

## Applying the bump

1. Update the version with `npm version <major|minor|patch> --no-git-tag-version`.
   This updates both `package.json` and `package-lock.json`.
2. Commit it on the PR branch as `chore(release): vX.Y.Z`.
3. In the PR description, state the chosen bump and list the commits that justify it.
4. After the PR is merged, tag the merge commit on `master`: `git tag vX.Y.Z`.

## Keeping it reliable

- Mark breaking commits when they are written, e.g. `feat(cli)!: make trpc the default API layer`,
  rather than relying on spotting breaks at release time.
- Tags make every release inspectable: `git log v1.0.0..v1.1.0` shows exactly what shipped.
